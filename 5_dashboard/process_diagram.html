Wafer Health 예측 대시보드 — 작동 프로세스

SK Hynix Wafer Test 기반 Field Health(RCC) 예측 결과를 모니터링하는 인터랙티브 대시보드의 동작 구조. 본 다이어그램은 챗봇·보고서 생성에 LLM(Claude API)이 연동된 상태를 가정합니다. 회색 점선 박스가 현재 mock → LLM 연동 시 채워지는 부분입니다.

React 19 + Vite (:5173) FastAPI + pandas (:8765) parquet 메모리 로드 TanStack Query 캐싱 LLM: Claude API · RAG

2 AI Agent 챗봇 — 자연어 질의 처리 흐름

예: 사용자가 "오늘 위험 wafer 알려줘" 라고 입력했을 때의 end-to-end 경로 (LLM 연동 가정).

1
User → Frontend
자연어 질문 입력
우하단 ChatbotWidget에 "오늘 위험 wafer 알려줘" 입력 또는 추천 질문 클릭.
2
Frontend → Backend
요청 전송 POST /api/chat
메시지 + 현재 화면 컨텍스트(선택한 split·페이지)를 함께 전송. SSE/스트리밍 응답 구독.
3
Backend (LLM 오케스트레이터)
의도 파악 + 도구 준비
시스템 프롬프트 + 사용 가능한 tool 스키마(데이터 API 래퍼)를 붙여 Claude API 1차 호출.
get_alerts_today()get_overview() list_wafers(status,sort)list_units(risk_only) unit_report(ufs)model_var_compare()
4
LLM → Backend (tool call)
필요한 데이터 호출 결정
Claude가 get_alerts_today() + list_wafers(status="today", sort="risk_ratio") 호출을 요청 → 백엔드가 in-memory DataFrame에서 즉시 조회해 결과 반환.
5
Backend (RAG)
도메인 지식 보강 (선택)
질문이 개념·근거 설명을 요하면 벡터 DB에서 관련 청크 retrieve (예: "위험 임계값=split별 pred 상위 5%", "ZITboost π·μ 의미", "PSI 0.25 경계").
6
LLM
최종 답변 생성
조회 데이터 + RAG 청크를 컨텍스트로 Claude 2차 호출 → "오늘 위험 wafer Top: L0421_w002(위험률 15.6%) … 주요 기여 변수 X1083(+2.3σ)" 형태의 근거 포함 답변을 토큰 스트리밍.
7
Backend → Frontend → User
답변 표시 + 화면 연동
ChatbotWidget이 스트리밍 출력. 답변 내 wafer/unit 링크 클릭 시 Drill-down으로 jump해 동일 데이터를 시각적으로 확인.

3 AI Agent — 위험 unit 보고서 자동 생성 흐름

Drill-down에서 위험 unit 선택 → "보고서 생성" 버튼 → LLM이 통계 근거를 엮어 HTML/PDF 산출.

1
User
Drill-down → Unit Diagnosis → "📄 보고서 생성" 클릭
대상 ufs_serial과 현재 wafer map 상태를 함께 전달.
2
Backend
진단 데이터 수집
/api/units/{id}/report (verdict·pred·π/μ·worst die·narrative) + /anomaly_features (z-score Top) + /model/shap·var-compare를 합쳐 구조화 JSON 구성.
3
LLM
보고서 문안 작성
"WARNING: pred 0.0234 — 상위 5% 임계 초과. (12,7) die가 최대 기여. X1083 +2.3σ, Cohen's d 0.78(p<10⁻⁶) — 위험을 가르는 강한 신호. 권고: 해당 lot 추가 검사 의뢰." 같은 PI용 narrative 생성.
4
Backend
렌더링 → 반환
narrative + wafer map 이미지 + SHAP bar + 통계 표를 템플릿에 끼워 HTML/PDF 생성 → 다운로드 응답.
5
User
의사결정 산출물
보고서를 근거로 검사 의뢰 / 격리 / 공정팀 알림 — 통계 근거가 첨부된 형태로 공유.

4 데이터 파이프라인 — 모델 산출물이 대시보드에 실리기까지

오프라인에서 1회 빌드 → 대시보드는 결과 parquet/json만 읽음. 모델이 갱신되면 ETL 재실행 후 data/ 교체.

① 모델링 실험
3_modeling/ ZITboost·Two-Stage·앙상블, Optuna HPO → 4_output/final/zit_only/{oof,val,test}_{die,unit}.csv + importance/PSI/var-compare
② ETL 스크립트
prepare_data.py · build_model_artifacts.py — CSV → parquet 변환, wafer/position 집계, normal baseline 산출
③ 5_dashboard/data/
die/unit/wafer parquet · overview_stats.json · unit_features · normal_baseline · position_stats · model/* (레포에 커밋됨)
④ FastAPI startup
DataStore가 전부 메모리 적재 + status/검사일 분배(데모) + wafer 재집계 + feature↔health Pearson r 계산 → /api/* 서빙
⑤ React + (LLM)
TanStack Query가 캐싱하며 화면 렌더 · ChatbotWidget/보고서는 같은 API를 LLM tool로 재사용
핵심 특징. ⓐ 대시보드 런타임은 읽기 전용 — 모델을 직접 호출하지 않고 미리 구운 예측 결과만 사용 (재현성·속도). ⓑ 5_dashboard/ 폴더만으로 자립 실행 (부모 프로젝트 의존 X). ⓒ status(today/pending/completed)와 검사일은 현재 데모용 분배 로직 — 실 운영 시 데이터의 실제 검사일 컬럼으로 교체. ⓓ ★ 표시 항목(LLM 오케스트레이터·RAG·/api/chat·/api/agent/report)은 본 다이어그램의 연동 가정 부분 — 현재 코드에서 ChatbotWidget은 키워드 기반 mock.
